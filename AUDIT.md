# Code audit — `hotspot-billing.zip`

Audited artefact: `hotspot-billing.zip` (33 entries, 16 files, 34,954 bytes uncompressed),
the Kotlin + shell project produced in the earlier chat that is preserved verbatim in
`Hotspot .txt`.

**Verdict: the design is sound, but the delivered code could not build, and the network
layer — the part that actually enforces billing — did not enforce anything.** Six findings
are build blockers, five are "the feature silently does nothing" bugs, and one is an
authentication bypass. Everything in the *Fixed* column below is fixed on this branch; the
rest is itemised under [Still open](#still-open).

---

## 1. What the project is supposed to do

```
Router1 (ISP) ──> rooted Infinix Hot 8 (NAT + DHCP + captive portal + vouchers + tc)
                       └──> Router2 ──> users
```

A user joins, an OS captive-portal sheet pops, they type a voucher code, the app binds that
code to their MAC, hands them a fixed IP, and caps their bandwidth for the voucher's
duration. A second device presenting the same code is refused.

That design is achievable on this hardware. The problems were in the implementation.

## 2. Facts established from the device log (`Hotspot .txt`)

These are read off the transcript, not assumed — several of them contradict the delivered
code.

## 4. Critical — the billing model did not actually hold

### F7 · Every user could bypass the voucher check (authentication bypass)
`setup_network.sh` set the default-deny policy and then immediately appended a rule that
undid it:

```sh
61:    iptables -P FORWARD DROP
62:    iptables -A FORWARD -i $LAN_IF -o $WAN_IF -j ACCEPT     # <-- accepts ALL LAN clients
```

(and line 44 did the same thing again). Result: any device on the LAN had unrestricted
internet without ever entering a voucher. Only ports 80/443 were redirected, so the portal
was a suggestion, not a gate.

**Fixed.** There is no blanket accept. The chain is built bottom-up so the final order is
per-client `ACCEPT` → return traffic → `REJECT tcp/443` → `DROP`; new authorisations are
always inserted above the deny. Asserted by `tools/run-script-selftest.sh`.

### F8 · The "static IP" never reached the client, so binding and shaping matched nothing
`IpPool.allocate()` picked e.g. `10.66.0.10`, then every firewall and `tc` rule keyed on
that address — but nothing ever told the client to use it. `dnsmasq` was configured with
`--dhcp-range=10.66.0.50,10.66.0.250` and **no** `--dhcp-host` reservations, so the client
kept its dynamic lease (`10.66.0.137`…). Therefore:

* `-m mac --mac-source X -s 10.66.0.10 -j ACCEPT` never matched → the paying user was blocked;
* `tc filter … match ip dst 10.66.0.10/32` never matched → **no bandwidth cap was ever applied**.

**Fixed.** New `reserve <mac> <ip>` / `unreserve <mac>` subcommands write
`dhcp-host=<mac>,<ip>` into a `--dhcp-hostsdir` and `SIGHUP` dnsmasq, which re-reads it
without a restart. The lease is now 10 minutes instead of 12 hours so a client migrates to
its reserved address promptly, and the firewall also accepts the client's *old* address
during that window so it does not go dark in between.

### F9 · HTTPS was DNATed to a plaintext HTTP server
```sh
58:    iptables -t nat -A PREROUTING -i $LAN_IF -p tcp --dport 443 -j DNAT --to-destination 10.66.0.1:8080
```
NanoHTTPD speaks HTTP, so every TLS handshake failed with a certificate error. On modern
Android/iOS that produces a "no internet" verdict and frequently **no captive-portal sheet
at all** — the opposite of the intended effect.

**Fixed.** Port 443 is no longer redirected; unauthenticated TLS gets
`REJECT --reject-with tcp-reset` so the client falls back to its plain-HTTP probe, which
*is* redirected.

### F10 · `tc filter del` as written cannot work; stale filters blackholed traffic
```sh
30:    tc filter del dev $LAN_IF protocol ip parent 1:0 prio 1 u32 match ip dst ${IP}/32 flowid 1:$CID
```
`tc` deletes filters **by handle**, not by match expression, so this always failed. The
filter stayed behind, its class was deleted on the next line, and every packet matching the
orphaned filter was then dropped into a non-existent class.

**Fixed.** `bandwidth_control.sh` keeps the authoritative class list in
`/data/local/tmp/hotspot_tc.state` and rebuilds the whole tree from it. Idempotent,
recoverable after the interface bounces, and there is no dangling-filter state to get wrong.
Verified by the self-test through an add → remove → re-add → duplicate-add cycle.

### F11 · Uploads were completely uncapped
Shaping was applied only to egress of `ap0` (downloads). Client → WAN traffic is *ingress*
on `ap0` and was never touched, so the upload half of every "plan" was unlimited.

**Fixed.** An `ingress` qdisc plus a `police` filter matched on **source** IP now caps the
upload direction at the plan rate.

## 5. High severity

| # | Finding | Where | Fix |
| --- | --- | --- | --- |
| F12 | `iptables -F` on start **and** stop wiped every table, including Android's own tethering and per-UID accounting chains — a good way to break the phone's own connectivity. Stop also ran `-P FORWARD ACCEPT`, i.e. fail-open. | `setup_network.sh:38,84,87` | Scoped deletes of only our own rules; no policy change; shaper torn down too |
| F13 | dnsmasq was started `--no-daemon &` from a script run by `su -c sh …`. When that shell exited the process was orphaned/killed — DHCP would randomly not be running. | `setup_network.sh:74` | Let dnsmasq daemonise; pidfile-tracked; `start` is now idempotent |
| F14 | No upstream resolver. | F15 | Every `authorize` did an unconditional `iptables -I`, and every reconnect added another copy. Rules and `authorized_macs.txt` grew without bound. | `setup_network.sh:50-52,97-99` | `-C` (check) before insert; state file rewritten de-duplicated |
| F16 | `deauthorize` deleted **one** copy of a rule (`-D` removes a single match), so after the duplicates piled up, revoking a voucher left access in place. | `setup_network.sh:105-106` | Loop `-D` until `-C` reports the rule gone |
| F17 | `classIdCounter = AtomicInteger(100)` reset to 100 on every process start, colliding with class ids already recorded in the database. | `net/VoucherManager.kt:20` | Seeded from `SELECT MAX(classId) FROM vouchers` |

## 7. Still open

Deliberately not fixed in this pass, because each is a feature rather than a defect, and
none can be validated without the physical phone:

- **O1 — No foreground service.** The portal server is started from `MainActivity.onCreate`
  and stopped in `onDestroy`, so backgrounding or killing the activity kills the captive
  portal while users are still connected. `FOREGROUND_SERVICE` is already in the manifest;
  what is missing is a `Service` with `foregroundServiceType="connectedDevice"` (API 34
  requires the type *and* `POST_NOTIFICATIONS`). **This is the highest-value next change.**
- **O2 — No admin screen.** `VoucherManager.generateBatch()` exists but nothing calls it;
  there is no way to create a voucher from the UI.
- **O3 — No expiry sweep.** `sweepExpired()` is never scheduled; `androidx.work` is an unused
  dependency until it is.
- **O4 — No usage accounting.** `UserSession.bytesUp/bytesDown` are never populated.
- **O5 — Portal security.** Vouchers travel in a plaintext HTTP POST on the LAN, so anyone
  on the network can sniff a live code; `/redeem` has no rate limit (8 chars from a
  32-symbol alphabet is brute-forceable given time) and no admin authentication at all.
- **O6 — STA+AP concurrency still unverified.** The log neither confirms nor denies it, and
  `iw` is not installed so the proposed check cannot run. Run instead, with WiFi connected
  *and* the hotspot on: `dumpsys wifi | grep -iE "concurren|softap|sta"`,
  `cat /sys/class/net/ap0/operstate`, `ip link`. If `ap0` will not come up alongside a
  connected `wlan0`, point `LAN_IF` at a USB-OTG Ethernet adapter (`eth0`/`usb0`) via
  `/data/local/tmp/hotspot.env`.
- **O7 — No watchdog** for Android's tethering service reconfiguring `ap0` underneath us.
- **O8 — Kernel module availability unverified on-device** (`xt_mac`, `sch_htb`, `act_police`).
- **O9 — Session lifetime is the voucher lifetime** from activation; no pause/resume, and no
  reconciliation between dnsmasq lease expiry and voucher expiry.
- **O10 — MAC spoofing is inherent** to MAC-based binding: a client that spoofs the bound MAC
  gets the session. Real mitigation is 802.1X or per-user PPPoE, not a bigger iptables ruleset.
- **O11 — `VoucherManager` has no unit tests** (needs in-memory Room / Robolectric).

## 8. What was verified, and what could not be

**Verified here**

* `tools/run-script-selftest.sh` — runs the **real** `setup_network.sh` and
  `bandwidth_control.sh` against stub `iptables`/`ip6tables`/`ip`/`tc`/`dnsmasq`/`sysctl`
  binaries and asserts the resulting rule set: 40+ assertions covering the default-deny
  ordering, the absence of the old blanket accept, portal rule order, idempotent
  authorisation, complete deauthorisation, scoped teardown, DHCP reservations, and the tc
  tree after an add/remove/re-add cycle. **All pass.**
* All three workflow YAML files parse and every `uses:` ref resolves to a real tag (checked
  against the GitHub API).
* `sh -n` on both shell scripts.

**Not verifiable in this sandbox** — stated plainly rather than assumed:

* **The Gradle/AGP build.** This environment has no JDK, no Android SDK, and no network
  route to `repo1.maven.org`, `services.gradle.org` or `dl.google.com` (all three fail at
  TLS, exit 35; only `github.com`, `pypi.org` and `registry.npmjs.org` are reachable).
  `./gradlew assembleDebug` therefore has to run in CI — that is exactly what
  `.github/workflows/apk.yml` is for, and the first PR run is the real compile check for
  F1–F5 and the Kotlin edits.
* Anything requiring the actual Infinix hardware: `ap0` behaviour, module availability,
  dnsmasq binding, and the OS captive-portal sheets.
